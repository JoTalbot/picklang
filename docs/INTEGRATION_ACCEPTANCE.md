# Локальная интеграционная приёмка availability

## Граница этой проверки

Это пример и воспроизводимая приёмка внутри picklang, а не интеграция с реальным
складом или репозиторием razborka. Чтение связанного документа потребителя через
GitHub API повторно вернуло 403. Его закреплённая версия PICK не изменялась;
реальную схему, набор enum и пользовательское одобрение необходимо согласовать
с владельцем потребителя. Ни один тест не делает сетевых или складских операций.

## Строгий контракт адаптера

`picklang.contracts` предоставляет небольшой контракт **плоского объекта со
скалярными полями**, а не JSON Schema и не sandbox:

```python
from picklang.contracts import ObjectContract, ScalarField, validated_tool

contract = ObjectContract({
    "id": ScalarField(str, nonempty=True),
    "status": ScalarField(str, choices=("available", "unknown", "error")),
})
checked = validated_tool(observe, contract, match_args={"id": "requested_id"})
```

Все объявленные поля обязательны, дополнительные запрещены. Типы точные, без
приведения (`True` не integer, `1` не boolean). Поддержаны str/bool/int/float;
NaN/Infinity запрещены. `nonempty` запрещает пустые/пробельные строки; данные
не обрезаются и не нормализуются. Enum чувствителен к регистру. Результат должен
быть обычным dict; возвращается независимая копия плоских данных. Привязанные
аргументы проверяются до вызова, совпадение идентификаторов — после ответа.

Обёртка сохраняет сигнатуру функции и бросает `ContractViolation` до передачи
результата в PICK/коммита активности. **Сам вызов адаптера уже состоялся**:
внешние эффекты самого адаптера не откатываются. Используйте наблюдающий адаптер,
а не операцию списания. Async-адаптеры этой обёрткой не поддержаны.

Пример полного контракта — `examples/availability_contract.py`: id, status,
freshness и conflict_status. Валидатор только проверяет факты. Статус `error`
является допустимым фактом технического отказа; PICK останавливает его до черновика.
Выбор пути не переносится в адаптер.

## Сценарий PICK

`examples/availability_review.pick`:

1. Получает проверенные факты через inventory.observe.
2. Разрешает утверждающий черновик только для available + current + none.
3. Для unknown, conflict, stale и present создаёт неутверждающий черновик review.
4. Ожидает сигнал approval. Только **boolean true** разрешает создание заявки
   на ручное рассмотрение; false и неправильные типы не вызывают review.submit.
5. Не подтверждает наличие товара и не разрешает конфликт автоматически.

Вложенный `@if approval` здесь выбран намеренно: условия проверяют точный boolean,
а старый guard `approval == true` в общей семантике выражений не является
универсальным валидатором типов. Сигнал None означает отсутствие сигнала/WAITING.
Источник и права отправителя сигнала должны проверяться внешней системой:
локальный deliver_signal сам не реализует аутентификацию оператора.

## Воспроизведение

```bash
pip install -e '.[dev]'
python -m pytest tests/test_tool_contracts.py tests/test_availability_acceptance.py -q
python examples/availability_demo.py
```

Покрыты выбор ровно одного пути, отсутствие submit до одобрения, unknown/conflict
без утверждения наличия, неверные enum/поля/типы/ID, технический error, отказ в
одобрении, crash после сохранения черновика и после сохранения submit, повторный
resume без повторного вызова уже сохранённых обработчиков.

Это доказательство поведения на локальных фикстурах, не exactly-once внешнего
submit при падении **внутри** операции. Для реального submit необходим стабильный
ключ идемпотентности и поддержка дедупликации внешним сервисом.

## Версионирование и replay

Валидация обёртки выполняется при настоящем вызове адаптера. Replay завершённой
активности использует сохранённый результат, проверяя CAS-хэш, и не вызывает
обёртку заново. При изменении схемы/реестра используйте новый execution_id либо
явную миграцию: digest исходника PICK сам по себе не фиксирует версию Python-
контракта. Не выдавайте старое исполнение за проверенное новой схемой.

## Что ещё требуется у потребителя

- Доступ к razborka и чтение его реального контракта, а не подмена этой фикстурой.
- Обновление pinned PICK и тесты на точном коммите потребителя.
- Версии схем, подлинность/права approval, бизнес-политика повторного рассмотрения.
- Идемпотентный внешний submit, fault injection с реальной тестовой инфраструктурой.

## Live A/B релиза 0.1.11

Запуск: https://github.com/JoTalbot/picklang/actions/runs/39878929979

GitHub сообщает об успехе live-каскада и парного quality/token-efficiency gate.
JSON-файлы сохранены в artifact `live-evaluation-9ac739869f82e6fee5bf403ddef3419bd1985f7d`.
При попытке скачать artifact из sandbox GitHub перенаправляет на недоступный
Azure Blob host. Поэтому покомпонентный численный анализ **не выполнен**, чисел
токенов, задержек, стоимости и повторов в этой приёмке не приводим.

После получения JSON нужно проверить pairing входов/модели, долю успехов,
полный расход prompt+completion tokens и attempts, задержки по каждой задаче и
условия провайдера. Денежная стоимость требует тарифов и данных billing;
одного PASS gate недостаточно, чтобы заявлять общий выигрыш по цене или скорости.
