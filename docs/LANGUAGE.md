# PICK — язык, спроектированный под автора-LLM

## Откуда берётся расход токенов у LLM — и что с этим делает PICK

LLM платит токенами не за «смысл», а за всё, что вынуждена печатать:

| Статья расхода | Как выглядит в Python/JSON | Что делает PICK |
|---|---|---|
| Бойлерплейт | импорты, классы, `def`, `try/except`, сериализация, объявления типов | Прелюдия среды подразумевается. Программа начинается сразу со смысла: `> order(id, amt)` |
| Механика надёжности | Ручная сага: список компенсаций, обратный проход, подсчёт откатов — в каждом проекте заново | `x = call ! undo` — одна строка. Механика (LIFO, идемпотентность) живёт в рантайме, а не в тексте от LLM |
| Ожидание/стражи | Циклы polling, проверки None, raise с текстами | `@wait approval`, `? cond -> fail "..."` — по одной строке |
| Повтор контекста при итерациях | На каждое изменение модель пересылает файл целиком | Diff-режим: `@base <digest>` + патч `~N:`/`+N:`/`-N`. Измерено: 45 токенов вместо 350 (Python целиком) — см. `bench_tokens.py` |
| Неоднозначность | Синонимы, идиомы, «как принято в этом проекте» → модель дообъясняет и ошибается | Одна конструкция на смысл, построчная грамматика, структурированные ошибки `line N: ожидается ...` — чинится одним маленьким патчем |
| Повторяющиеся куски | Копипаст типовых блоков | Блоки адресуются в CAS по хэшу; словарь проекта (vocabulary) даёт короткие имена дорогому контексту |

Замеры на примерах из `examples/` (tiktoken, cl100k_base): сага оплаты — 121 токен
против 350 у эквивалентного Python и 305 у JSON-воркфлоу (2.5–2.9x); агент с
human-in-the-loop — 111 против 229 (2.1x); итерационный патч — ещё 2.7x сверху.

Честная граница: PICK не делает короче *уникальную* логику. Если шаг — нетривиальный
алгоритм, он живёт в функции хоста на обычном языке, а PICK лишь вызывает её по имени.
PICK сжимает оркестрацию, надёжность и итерации — то, чем LLM занята большую часть
времени в реальной разработке.

## Грамматика v0.1 (вся)

```
# комментарий
> name(a, b)                 цель: имя программы и её входы
x = mod.fn(a, 1, "s")        вызов хост-функции, результат в x
x = mod.fn(a) ! mod.undo(x)  шаг саги: компенсация при позднейшем сбое (LIFO)
? x.ok -> fail "причина"     страж
@wait approval               durable-пауза до внешнего сигнала; значение -> в approval
a >> b.f(3) >> c.g()         пайплайн: результат слева — первый аргумент справа
out {k: x, t: y.tx}          результат программы
```

Выражения: вызовы, переменные, доступ к полям `p.tx`, литералы (числа, строки,
списки), карты `{k: expr}`. Одна строка — один шаг. Никаких блоков и отступов.

## Ошибки как интерфейс для LLM

Парсер не говорит «SyntaxError где-то». Он говорит, на какой строке и что именно
ожидалось (`line 4: страж записывается как: ? условие -> fail "..."`). Для модели
это разница между «перепиши всё» (~все токены) и «почини строку 4» (~10 токенов).
Тот же принцип — в diff-режиме: патч к несовпавшему digest базы запрещён, модель
не может молча изменить программу, которую не видела.

## Расширения первой волны

- **Словарь проекта**: `&alias(a, b)` разворачивается в блок из CAS-словаря
  (`picklang/vocab.py`); тело блока хранится один раз по digest.
- **Minify**: `compress()` переименовывает переменные в `a, b, c...` и отдаёт
  source-map; `expand()` восстанавливает читаемые имена. Функции хоста и строки
  не переименовываются.
- **Genesis**: `generate(intent_dict)` собирает программу из намерения — модель
  платит только за шаги, компенсации и стражей, а не за синтаксис.
- **Исправление ошибок**: `suggest_patches()` возвращает готовые `~N:`-патчи,
  `fix_source()` применяет их. Статический контроль — `check_source()` до запуска.

## Ограниченное ветвление (issue #63)

```pick
> choose(fact)
@if fact.status == "available" and fact.freshness == "current" and fact.conflict_status == "none"
    out strict.draft(fact.id)
@else_if fact.status == "unknown"
    out review.draft(fact.id)
@else
    ? false -> fail "unsupported facts"
@end
```

Это пример выбора ветви, а не полная проверка входной схемы. Полный пример с
проверкой enum и идентификатора — `examples/availability.pick`. Он только выбирает
тип черновика, не проводит складские операции и не разрешает конфликт автоматически.
В нём `review.draft` означает неутверждающий черновик для ручного рассмотрения.

### Грамматика и ограничения

- Блок: `@if condition`, ноль или больше `@else_if condition`, необязательная
  единственная `@else`, обязательный `@end`. Вложенность — максимум 8.
- Отступы косметические. Пустые ветви, лишние или незакрытые директивы — ошибки.
- В ветвях поддержаны присваивания, выражения, guards, `out`, простой `@wait`
  и вложенные conditional-блоки. Циклы, параллельные группы, бюджеты, task cards,
  объявления цели и wait timeout/else внутри ветки пока отклоняются парсером.
- Условия: boolean-литералы/переменные/поля, сравнения `== != < <= > >=`,
  `not`, `and`, `or` и скобки вокруг условий; приоритет: `not`, `and`, `or`.
  Вызовы инструментов, pipeline и создание словарей в условиях запрещены.
- Допустимы только обычные JSON-подобные скаляры: boolean, string, int и конечный
  float. Сравниваемые операнды обязаны иметь один точный тип (`true != 1` не
  вычисляется, а завершается ошибкой типов). `null`, контейнеры, NaN/Infinity,
  отсутствующие переменные/поля и пользовательские объекты запрещены.
- Условие обязано дать именно boolean; truthiness строк, чисел или объектов нет.
  Поля читаются только из словарей, не через свойства Python-объектов.
- До исполнения выбранной ветви проверяются **все условия текущего блока**.
  `and/or` также проверяют все операнды: неизвестное поле не скрывается за
  коротким замыканием. Условия вложенного блока проверяются только при входе
  в него. Затем выполняется первая истинная ветвь, иначе `@else`. Если ничего
  не подошло и `@else` нет — безопасный отказ, а не молчаливый пропуск.

### Область видимости и статическая проверка

Ветка читает внешний контекст, но не может присваивать внешним переменным.
Её новые переменные и сигналы локальны; после `@end` они недоступны. Результат
`out` сохраняется; как и раньше, `out` задаёт результат и не является `return`.
Компенсации сохраняют контекст завершённого шага, включая локальные результаты.
Одобрение и taint-контекст ветки не распространяются наружу.

Checker проверяет все ветви: неизвестные переменные/функции, арность,
локальность присваиваний и несовместимые известные типы одноимённых присваиваний.
Известные неверные типы условий — ошибки. Отсутствующие поля статически известного
словаря и поля, отсутствующие в переданном контракте результата функции, — ошибки
условия. Без схемы динамические поля/типы проверяет runtime: checker не утверждает,
что произвольный ответ адаптера соответствует схеме или допустимому enum.

### Поддержка backend

Canonical IR хранит `kind: conditional` с упорядоченным списком `cases`, каждый
содержит `condition` (либо null для else) и `steps`. Интерпретатор и локальный
`run_pick()` поддерживают блоки, сигналы и replay выбранного пути.
AOT явно отклоняет conditional; `run_program()` автоматически выбирает интерпретатор.
Оба Temporal-адаптера отклоняют такую программу до первого шага.
`prove_safety()` консервативно проверяет каждую ветвь, включая вложенные, и не
переносит локальное approval за `@end`. Для опасного шага требуются предшествующие
`@wait approval` без timeout и положительный guard (`? approval -> fail ...`
или сравнение approval с литералом true). Внешнее проверенное approval наследуется
ветвями; одобрение в одной ветви не покрывает другую. Анализ также обходит циклы,
parallel и вызовы внутри out/map. Это проверка порядка известных эффектов по
именам и @fx, а не доказательство безопасности произвольного Python-обработчика;
неизвестные динамические эффекты требуют контрактов и ручного аудита.
