# Релизный контрольный список

Этот список отделяет локально воспроизводимые проверки от live-проверок, зависящих от доступности Groq и квот бесплатных моделей. Релиз `0.1.12` опубликован 2026-11-11; последний опубликованный релиз — `v0.1.12`. Следующий релиз не планируется до накопления проверенных изменений.

## Автоматически проверяется в GitHub Actions

- [ ] Репозиторий и SHA запуска совпадают с актуальным `main`.
- [ ] Все тесты из `tests/` проходят, включая регрессию общего HTTP-дедлайна.
- [ ] Собираются wheel и source distribution.
- [ ] CLI запускается, демонстрационный сценарий завершается.
- [ ] Offline regression suite подтверждает batch/capability/taint/approval/durable-hook контракты и MCP request-ID integrity.
- [ ] Live-каскад выполняет двенадцать задач, включая страж, сагу с откатом, `@wait`, параллельные ветви и бюджет; сводка публикуется в логах и Job Summary с сохранением JSON-телеметрии в Actions artifacts на 30 дней. Live-запуск выполняется только вручную через workflow_dispatch с явным `run_live=true`; значение по умолчанию — false. Обычный push в main и PR не вызывают Groq и не расходуют API-квоту.

## Проверки перед публикацией релиза

1. Проверить одинаковую версию в `pyproject.toml`, picklang.__version__, durable_weave.__version__, заметках релиза и Git-теге.
2. Установить wheel в чистое виртуальное окружение и проверить `pick --help` и демонстрацию.
3. Проверить содержимое wheel и sdist: пакетные модули, README и лицензионные метаданные.
4. Выполнить полный набор тестов повторно на точном коммите, который будет отмечен тегом.
5. Если владелец отдельно разрешил расход API-квоты, вручную запустить workflow_dispatch с `run_live=true`, затем проверить live-результаты и ошибки API. Пропущенный live job не считается успешной live-проверкой; успешный прогон не гарантирует доступность бесплатных моделей в будущем.
6. Публикация релиза не выполняется автоматически при push в main. Только отдельный ручной запуск с `publish_release=true` и `run_live=true` может создать GitHub Release после успешных обязательных проверок; не перезаписывать уже опубликованный тег.

## Интерпретация live-метрик

Результаты Groq — снимок конкретного запуска. Модель, число попыток, задержка и расход токенов могут меняться между запусками. Исторические таблицы в документации нельзя считать результатом текущего запуска; текущие значения находятся в логах и Job Summary соответствующего workflow run.

## Автоматическая публикация

Обычный push в main выполняет offline-проверки и не вызывает live Groq/API, не создаёт тег и не публикует релиз. Live-каскад запускается только при ручном `workflow_dispatch` с `run_live=true`. GitHub Release требует отдельного `publish_release=true` в том же ручном запуске, а также успешных unit-тестов, Temporal-интеграции, сборки/проверки пакета и live-каскада с парным A/B gate. Уже существующий релиз не перезаписывается; если тег уже существует без Release, публикация останавливается с ошибкой для ручного разбора. Релизный job выполняется на доверенном self-hosted Linux ARM64 runner с `contents: write`; PR-код запускается только на GitHub-hosted runners.
