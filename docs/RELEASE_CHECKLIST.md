# Релизный контрольный список

Этот список отделяет локально воспроизводимые проверки от live-проверок, зависящих от доступности Groq и квот бесплатных моделей.

## Автоматически проверяется в GitHub Actions

- [ ] Репозиторий и SHA запуска совпадают с актуальным `main`.
- [ ] Все тесты из `tests/` проходят, включая регрессию общего HTTP-дедлайна.
- [ ] Собираются wheel и source distribution.
- [ ] CLI запускается, демонстрационный сценарий завершается.
- [ ] Live-каскад выполняет двенадцать задач, включая страж, сагу с откатом, `@wait`, параллельные ветви и бюджет; сводка публикуется в логах и Job Summary с сохранением JSON-телеметрии в Actions artifacts на 30 дней. Текущий workflow запускает live-каскад после успешных проверок на push в main, а также допускает ручной workflow_dispatch с run_live=true. Это расходует квоту Groq и должно учитываться при каждом слиянии.

## Проверки перед публикацией релиза

1. Проверить одинаковую версию в `pyproject.toml`, picklang.__version__, durable_weave.__version__, заметках релиза и Git-теге.
2. Установить wheel в чистое виртуальное окружение и проверить `pick --help` и демонстрацию.
3. Проверить содержимое wheel и sdist: пакетные модули, README и лицензионные метаданные.
4. Выполнить полный набор тестов повторно на точном коммите, который будет отмечен тегом.
5. При доступной квоте вручную запустить workflow_dispatch с run_live=true, затем проверить live-результаты и ошибки API. Пропущенный live job не считается успешной live-проверкой; успешный прогон не гарантирует доступность бесплатных моделей в будущем.
6. Создавать тег и GitHub Release только после успешных обязательных проверок; не перезаписывать уже опубликованный тег.

## Интерпретация live-метрик

Результаты Groq — снимок конкретного запуска. Модель, число попыток, задержка и расход токенов могут меняться между запусками. Исторические таблицы в документации нельзя считать результатом текущего запуска; текущие значения находятся в логах и Job Summary соответствующего workflow run.

## Автоматическая публикация

После слияния коммита с новой версией в `pyproject.toml` workflow публикует GitHub Release только если unit-тесты, отдельная Temporal-интеграция, сборка/проверка пакета и live-каскад Groq с парным A/B gate завершились успешно. Уже существующий релиз не перезаписывается; если тег уже существует без Release, публикация останавливается с ошибкой для ручного разбора. Релизный job выполняется на доверенном self-hosted Linux ARM64 runner с `contents: write`; PR-код запускается только на GitHub-hosted runners.
