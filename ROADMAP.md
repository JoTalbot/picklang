# Дорожная карта PICK / DurableWeave после v0.1.10

Дата плана: 2026-10-21. Базовая версия: `v0.1.10`.

Цель проекта: сделать PICK заметно удобнее классического агентного цикла, дешевле по **фактическим расходам API**, быстрее на типичных задачах и надёжнее при сбоях. Это план инженерных этапов и критериев выхода, а не обещание заранее известных результатов. Этапы выполняются небольшими PR, параллельно только там, где нет зависимости по интерфейсам или данным.

## Текущая точка

- `v0.1.10` опубликован; main CI прошёл: unit/package checks, live Groq cascade и публикация релиза.
- Последний live cascade: 12/12 задач, 12 попыток, 3 434 токена, сумма длительностей задач 3,9 с. Это один снимок, а не гарантия будущих результатов.
- Парный PICK vs classic Python ранее показал 1 703 против 2 105 токенов на одном прогоне (экономия 19,1%). Выборка слишком мала для общего заявления о превосходстве.
- Локальный корпус исходников: 609 токенов PICK против 942 Python на 8 задачах. Это только размер исходников, не полный расход агентного цикла.
- В репозитории уже есть парсер/IR/интерпретатор, diff-патчи, словарь CAS, статические проверки, durable-журнал/CAS, саги, ожидания, budgets, result projections, MCP и опциональный Temporal-адаптер.
- Открытых PR и issues на момент подготовки плана нет.

## Правила выполнения

1. Сначала корректность и воспроизводимые измерения, потом оптимизация. Не оптимизировать по одному удачному live-прогону.
2. Каждый этап делить на небольшие изменения: тесты → реализация → документация → PR → CI → merge → release только при необходимости.
3. Любое преимущество публиковать только с методикой, числом повторов, распределением, model ID, фактическими input/output tokens, wall-clock временем, стоимостью по зафиксированным тарифам и оценкой качества.
4. Live-тесты расходуют API-квоту. Запускать их на доверенном main или вручную, когда нужен ответ на конкретный вопрос; обычные PR должны оставаться без секретов.
5. Не заявлять exactly-once для внешних побочных эффектов. Требовать идемпотентность, ключи операций и явно документировать окна сбоя.
6. Не запускать пользовательский PR-код на self-hosted runner с секретами. Сохранить защиту от устаревших запусков, ограничение concurrency, таймауты и минимум разрешений.
7. Не повышать версию ради формального прогресса. Выпускать версию, когда накоплен полезный и проверенный набор изменений.

## Этапы

### Этап 0. Зафиксировать исходную линию и критерии успеха
**Приоритет: P0 · первый**

- Сохранить воспроизводимый snapshot текущих тестов, live cascade и paired benchmark.
- Проверить, что результаты связаны с SHA коммита, конфигурацией модели, repeat count и временем запуска.
- Разделить метрики на: качество/семантический паритет, токены, стоимость, wall-clock latency, число запросов/повторов, устойчивость к сбоям.
- Проверить, что отчёт явно помечает пропущенные/неполные измерения и не превращает отсутствие телеметрии в ноль.
- Зафиксировать минимальный набор сценариев: обычный успех, ошибка/repair, retry, saga rollback, wait/approval, parallel, budget stop, большой tool response.

**Выход:** baseline-отчёт, пригодный для повторного сравнения; все claims снабжены оговорками.

### Этап 1. Доказуемая корректность и паритет
**Приоритет: P0**

- Расширить golden/property-based тесты парсера, сериализации, diff/apply, интерпретатора и AOT.
- Проверить эквивалентность PICK и эталонных реализаций на одних входах и одинаковых побочных эффектах.
- Добавить негативные случаи: malformed input, глубокая вложенность, неизвестные функции/поля, дублирующиеся события, повреждённый CAS и прерванный журнал.
- Проверить, что проверки статического IR не блокируют корректные программы и отклоняют опасные/некорректные.
- Зафиксировать совместимость грамматики и формат IR; изменения несовместимости сопровождать версионированием/миграцией.

**Критерий выхода:** все golden/property tests проходят; нет необъяснённых расхождений; найденные ошибки имеют regression test.

### Этап 2. Удобство разработчика и CLI
**Приоритет: P1**

- Сделать единый понятный workflow: создать/проверить/запустить/проверить статус/посмотреть trace.
- Улучшить сообщения об ошибках: номер строки, причина, ближайшее исправление/patch, не выводя секреты и полные чувствительные payloads.
- Добавить JSON-формат результатов для CI и скриптов; стабильные exit codes.
- Улучшить примеры «с нуля до работающей программы» и отдельный tutorial для diff, vocabulary, saga, wait, budgets и tool projection.
- Проверить установку wheel в чистой среде на поддерживаемых Python/OS и ясность optional dependencies.

**Критерий выхода:** новый пользователь может установить пакет, выполнить пример, диагностировать намеренно сломанную программу и получить машинно-читаемый результат без чтения исходников проекта.

### Этап 3. Честный end-to-end benchmark и экономика
**Приоритет: P0 · основной исследовательский этап**

- Расширить парный набор минимум до 20–30 задач с PICK, Python и при необходимости JSON/workflow baseline.
- Для каждого baseline заранее определить одинаковые требования, входы, tool outputs и критерии правильности.
- Разделить токены исходника, полные input/output tokens API, стоимость, wall-clock latency и локальное время исполнения.
- Выполнять одинаковое число повторов, чередовать порядок вариантов, фиксировать модель/параметры/версию промпта; считать медиану и разброс, отмечать неудачные/цензурированные прогоны.
- Считать стоимость по явно версионируемой таблице тарифов; неизвестные цены помечать неизвестными, не подменять нулём.
- Измерять полную стоимость настройки vocabulary/CAS и амортизировать её по нескольким задачам; показывать точку безубыточности.
- Не принимать сравнение, если семантический паритет не подтверждён.

**Критерий выхода:** один воспроизводимый отчёт сравнивает качество, стоимость и скорость; CI проверяет целостность отчёта, а не навязывает победу PICK. Порог выигрыша назначать после получения нескольких стабильных baseline-замеров.

### Этап 4. Контекст и инструменты агентов
**Приоритет: P1**

- Проверить projections/limits/CAS refs на больших и вложенных ответах инструментов.
- Измерить tool-result truncation против полного контекста, включая потери информации и правильность конечного ответа.
- Улучшить безопасную маркировку недоверенных данных и границу «данные, не инструкции».
- Проверить семантический кеш: ключ должен учитывать все факторы, влияющие на результат; секреты и персональные данные не должны попадать в логи/ключи.
- Проверить routing/cascade и prefetch: меньше запросов без падения качества; лимиты/отмена должны работать предсказуемо.

**Критерий выхода:** на репрезентативном наборе измеряется снижение полного расхода токенов/стоимости при неухудшении качества в заранее заданных пределах.

### Этап 5. Durable execution и восстановление
**Приоритет: P0**

- Провести матрицу fault-injection: падение до/после записи CAS, между записью артефакта и события, во время wait, во время compensation, при конкурирующих resume/signal.
- Проверить атомарность SQLite/CAS, блокировки, дедупликацию и восстановление после повреждения/частичной записи.
- Сделать идемпотентность внешних действий частью явного контракта и примеров.
- Проверить replay determinism: время, случайность и внешние ответы должны фиксироваться или задаваться через интерфейсы.
- Добавить понятные recovery-команды и отчёт «что было подтверждено / что требует ручной проверки».

**Критерий выхода:** fault-injection-тесты доказывают заявленные локальные гарантии; документация перечисляет границы и сценарии, где требуется ручное вмешательство.

### Этап 6. Параллельность, отмена и управление ресурсами
**Приоритет: P1**

- Проверить конкурирующие ветки, детерминированный merge результатов, исключения, отмену и дедлайны.
- Ввести/проверить ограничения параллелизма, общий deadline, token/request budget и backpressure.
- Проверить, что hedge/speculation не удваивают побочные эффекты и отменяют проигравшие ветки безопасно.
- Добавить benchmark на p50/p95/p99 и стоимость при разных уровнях concurrency.

**Критерий выхода:** измеренный выигрыш latency при контролируемой стоимости и отсутствие гонок/дублированных эффектов в стресс-тестах.

### Этап 7. MCP и внешние интеграции
**Приоритет: P1**

- Проверить таймауты, retries, rate limits, schema validation и корректное закрытие MCP-процессов/пулов.
- Явно задавать capability allowlist для каждого инструмента и минимальные права.
- Добавить contract tests на ошибки сервера, неверные схемы, большие ответы, таймаут и отключение.
- Документировать настройку без раскрытия секретов и безопасное хранение credentials.

**Критерий выхода:** интеграции имеют проверяемые контракты и предсказуемое поведение при отказах; не требуется доверять тексту ответа инструмента как инструкции.

### Этап 8. Temporal и распределённый backend
**Приоритет: P2 · после укрепления локального durable-ядра**

- Сначала отделить общие контракты backend от специфики локального executor и Temporal.
- Проверить retries, signals, timers, worker restart, versioning и детерминизм workflow.
- Использовать отдельный интеграционный CI job/service; не считать «не удалось запустить Temporal» успешным пропуском.
- Проверить совместимость истории workflow с обновлениями и определить правила безопасного rollout.
- Документировать эксплуатационные затраты, сервисные зависимости и ситуации, где локальный backend проще и лучше.

**Критерий выхода:** end-to-end тест переживает перезапуск worker и продолжает тот же workflow; версия истории и границы гарантии документированы.

### Этап 9. Безопасность и аудит
**Приоритет: P0/P1, непрерывно**

- Проверить обработку secrets, недоверенных tool outputs, path traversal, чрезмерных payloads, DoS через глубину/циклы и утечки в trace.
- Проверить цепочку хэшей, CAS verification, подпись/аттестацию отчётов и экспорт audit trail.
- Добавить security regression tests и dependency review; зафиксировать политику раскрытия уязвимостей.
- Описать модель угроз: локальный процесс, внешний инструмент, недоверенная программа, повреждение хранилища, скомпрометированный worker.
- Не обещать криптографическую подпись происхождения, пока нет управления ключами, ротации и проверки подписи.

**Критерий выхода:** заявленная модель угроз покрыта тестами; аудит может независимо проверить целостность артефактов и событий.

### Этап 10. Упаковка, документация и готовность к выпуску
**Приоритет: P1, каждый релиз**

- Проверять wheel/sdist, CLI, примеры и optional dependencies в чистой среде.
- Автоматически проверять соответствие версии, release notes, тега и опубликованного артефакта.
- Проверить, что PR-код запускается только на GitHub-hosted runner, секреты доступны только доверенным live jobs, а stale/concurrent jobs не тратят квоту.
- В релизных заметках указывать реальные изменения, известные ограничения и ссылки на результаты CI.
- Поддерживать migration/compatibility notes для изменений грамматики, IR и durable history.

**Критерий выхода:** release checklist проходит на точном коммите, а опубликованный тег соответствует проверенному артефакту.

## Рекомендуемый порядок ближайших работ

1. **PR A:** baseline и формат отчёта end-to-end benchmark, проверка полноты телеметрии.
2. **PR B:** расширение парного корпуса и semantic parity на одних входах.
3. **PR C:** повторяемый live benchmark с ограниченным числом запусков и корректной статистикой.
4. **PR D:** fault-injection матрица durable executor/CAS/SQLite.
5. **PR E:** улучшения CLI и JSON-результатов на основе обнаруженных пользовательских трений.
6. **PR F:** benchmark projections/cache/cascade на реальных размерах tool outputs.
7. **PR G:** concurrency, cancellation, deadlines и hedge safety.
8. **PR H:** MCP contract tests и security hardening.
9. **PR I:** Temporal distributed integration, только после локальных гарантий.
10. **PR J:** документация эксплуатации, release automation audit и релиз, когда накоплены проверенные изменения.

Параллельно можно вести документацию, аудит CI и тесты безопасности. Не параллелить изменения формата IR, benchmark schema и runtime semantics без предварительно согласованного контракта.

## Решения, которые нужно принимать по данным, а не заранее

- Насколько PICK дешевле в полном цикле: пока не доказано с достаточной выборкой.
- Какой режим каскада/hedge лучше: зависит от распределения задержек, тарифа и rate limits.
- Нужен ли Temporal конкретному развёртыванию: только если нужны распределённые workers, долгие workflow и внешние сигналы.
- Какие функции должны стать стабильным публичным API: после проверки реального использования и совместимости.
- Какой минимальный порог качества/экономии блокирует релиз: определить по baseline и целям пользователя, а не подгонять под уже полученный результат.

## Определение готовности проекта к зрелому релизу

Проект можно считать готовым к зрелому публичному использованию, когда:
- семантический паритет подтверждается расширенным корпусом;
- полный цикл измеряется воспроизводимо и показывает качество/стоимость/latency, включая неудачные прогоны;
- recovery и безопасность проверены fault-injection/security тестами;
- CLI и документация позволяют начать без чтения исходников;
- интеграции имеют contract tests, а распределённый backend не маскирует ошибки;
- релизы воспроизводимы, артефакты проверяются, а ограничения явно описаны.

Это не означает, что каждый этап обязан привести к функции. Если измерения покажут отсутствие пользы или слишком высокую сложность, соответствующее направление следует отложить или удалить.
